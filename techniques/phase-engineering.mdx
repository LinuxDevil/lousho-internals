## The pattern

Phase engineering pipelines a job through named phases — `spec → plan → implement → verify → report` — where *the harness, not the model, owns the ordering*. The model fills `llmCall` nodes; `toolCall` nodes run real checks (tests, linters); `oneOf` routes on the verdict. `examples/phase-pipeline/` implements it on `FlowBuilder`/`FlowExecutor`.

Contrast with wave engineering: waves bound *parallel breadth*; phases bound *sequential order*. Both exist because the agent loop can't guarantee either.

## Why it's built this way

- **The retry ladder is unrolled, not looped.** `FlowExecutor` has no runtime `loop` node (it's editor-shape-only — `LOUSHO_FLOW_INVALID`), so N attempts are N `oneOf`-guarded attempt nodes. Static, inspectable, finite — [flow vs. loop](/design/flow-vs-loop).
- **`return`/`end` don't early-exit.** A sequence always runs every step — routing is expressed by `oneOf` branches containing whole sub-sequences, not by bailing mid-phase. The pipeline example was built around exactly this.
- **Proof gates are `toolCall` nodes, not model opinion.** "Did it work?" is answered by running `check` (a `defineTool` that executes the proof command) and branching on its `'PASS:'/'FAIL:'` string — the model can't talk its way past a failing test.
- **Two expression regimes, by design.** `{{var}}` interpolation is flat text (`\w+`, no dots) for prompts; `oneOf` conditions use `evaluateSafeExpression` with property paths and `startsWith`/etc. The pipeline seeds a flat `check.feedback` string because `{{check.feedback}}` literally can't resolve — knowing which regime you're in is the working knowledge.
- **Plain `AgentConfig`, not a live agent.** A flow's steps run under `{ name, prompt?, settings }` — `isCreateAgentResult` rejects `createAgent()` output (LOU-R14); a built agent runs *itself*.

## How it composes

```text
sequence
  ├─ llmCall  spec        → outputVariable: spec
  ├─ llmCall  plan        → outputVariable: plan
  ├─ llmCall  implement   → outputVariable: impl        (attempt 1)
  ├─ toolCall check(impl) → 'PASS:…' | 'FAIL: <feedback>'
  ├─ oneOf    fail? → llmCall implement (attempt 2, seeded w/ feedback) → toolCall check → oneOf …
  └─ llmCall  report      — composes spec + impl + check verdict into the deliverable
```

Reaching `report` after the ladder means every attempt failed or passed — the report phase exists precisely so the deliverable is *composed*, not whichever `impl` happened to be last.

## Example

```ts
{ type: 'oneOf', options: [
  { condition: 'check.startsWith("PASS")', step: reportPhase },
  { step: { type: 'sequence', steps: [retryImpl, checkAgain] } },
]}
```

`examples/phase-pipeline/`: 7 offline tests (`mockModel` + scripted phases), live run on OpenRouter — 17 steps, gate passed, report composed.
