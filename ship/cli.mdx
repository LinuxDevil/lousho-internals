title: "The lousho CLI"
description: "How bin/lousho.js dispatches to src/cli/*: one strict parseArgs wrapper, per-command run* entry points that return exit codes, and what each command does internally."
---

The `lousho` binary is a thin CommonJS dispatcher (`bin/lousho.js`) that maps a command name to a `run*` function in `dist/cli/`, lazy-`require()`d per invocation. Every command parses argv with the shared strict parser in `src/cli/args.ts`, does its work, and resolves with a process exit code — no command calls `process.exit()` itself, so each is unit-testable with injected IO.

## Entry points

- `bin/lousho.js` — `COMMANDS` map (`init`, `dev`, `chat`, `acp`, `add`, `build`, `studio`, `mcp`, `doctor`, `eval`, `traces`, plus `help`/`-h`/`--help`). Unknown or missing command prints `USAGE` to stderr and exits 1.
- `src/cli/args.ts` — `parseCommand(spec, args)`: `node:util` `parseArgs` in strict mode. `--flag value` and `--flag=value` both work; `multiple: true` flags accumulate; `--` ends flags; `-h`/`--help` is added to every command and short-circuits validation. A value starting with `-` needs the `=` form (`--model=-x`). `usageError()` throws `SDKError` code `LOUSHO_CONFIG_INVALID` with the usage line as `hint`. `takeOptionalValueFlag()` handles `--traces[=dir]`, the one flag whose value only binds via `=` (so `--traces agent.yaml` stays flag + path). `portValue()` validates 0–65535.
- Per command: `parse*Args()` then `run*(rest, io?)` returning `Promise<number>` — e.g. `runDev` (dev.ts), `runBuild` (build.ts), `runEval` (eval.ts), `runDoctorCommand` (doctor.ts), `runAdd` (add.ts), `runInit` (init.ts), `runChat` (chat.ts), `runAcp` (acp.ts), `runMcp` (mcp.ts), `runStudio` (studio.ts), `runTraces` (traces.ts).
- `src/server/chatRoutes.ts` / `src/server/fetchRoutes.ts` — the `/chat` routes `dev`, `chat`-adjacent servers and the deployed node server all share (not CLI code, but the seam every serve command hangs on).

## How it works

Every command module follows the same shape: a `USAGE` string and a `CommandSpec`, a pure `parse*Args`, then a `run*` that catches errors, prints them in the command's voice, and resolves the exit code. What each does internally:

- **`dev`** (`dev.ts` + `devReload.ts`): `detectTarget()` classifies the positional path — directory → agent dir, `.yaml`/`.yml`/`.json` → spec file, `.ts`/`.js` → module export. `startReloader()` loads it, watches its sources, and hot-swaps a rebuilt agent into a mutable `DevState` holder; a failed reload is logged and surfaced in the UI while the last good agent keeps serving. `startDevServer()` binds `127.0.0.1:3737` by default (explicit `--host` to opt into LAN), pre-flights `EADDRINUSE`, and routes `GET /health`, `GET /dev/status`, `GET /` (the `dev-ui/index.html` chat UI), channel mounts, and `/chat` — the same `handleChatRequest`/`serveFetch` routes the deployed node server uses. `--traces[=dir]` injects a `fileTraceExporter`; `--no-schedules` skips `startSchedules`.
  - Module targets deserve a note: `loadModuleAgent` imports the file with a `?t=` cache-busting query (`withFreshImports`, so reloads see new code), and the default/`agent` export may be a built `SimpleAgent` (`isSimpleAgent` checks `send`+`close`) *or* a `createAgent()` config (`isAgentConfig` checks `instructions`/`prompt`). `createAgentConfigOf` remembers how a prebuilt agent was configured, so an `overrides.exporter` (`--traces`) still reaches its runs by rebuilding it; `storeOwners` (a `WeakSet`) marks agents that own a store so `dev`'s shared session store doesn't double up.
- **`chat` / `acp`** (`chat.ts`, `acp.ts`): `buildAgent()` (exported from `chat.ts`, shared by `acp`) reuses `detectTarget`/`loadTarget` from `devReload`; `--model provider/model` rewires a spec's provider or overrides a dir/module agent's model. `chat` runs `runChatRepl` (`chatRepl.ts`) — streams each turn's events, handles approvals/questions/sign-ins inline, and runs slash commands (`/new`, `/compact`, `/clear`, `/model`, `/history`, `/quit`); `--session` resumes an id, `--store sqlite:<file>` lazily imports `SqliteStore`, and `--traces[=dir]` attaches a `fileTraceExporter`. `acp` serves `serveAcp` on stdio — stdout carries only protocol frames, everything else goes to stderr.
- **`build`** (`build.ts`): registers built-in adapters plus a `stub` test adapter, then drives `getAdapter(--target)` through `scaffold() → build() → describe()`; output defaults to `.lousho/build/<target>`. See [build targets](/ship/build-targets).
- **`eval`** (`eval.ts` + `evalReport.ts`): resolves the *project's* vitest via `createRequire(cwd).resolve('vitest/package.json')` (exit 2 with the install line when absent), writes a generated `vitest.eval.config.mjs` plus an empty `results.jsonl` into a fresh `os.tmpdir()` dir, and spawns `vitest run` with `VITEST_*` vars scrubbed and `RESULTS_ENV`/`TAGS_ENV`/cassette/`REMOTE_URL_ENV` injected. Results come back over the JSONL file (not a custom reporter — see `src/evals/recorder.ts`), then `renderTable`, `renderDriftTable`, `renderJunit` (`--junit`, `testsuites`→`testsuite` per eval→`testcase` per case), `renderJson` (`--json`). Exit: 0 pass, 1 gate failure (or `--strict` soft failure, or vitest itself failing), 2 cannot run. `--record`/`--replay`/`--drift` are mutually exclusive (`LOUSHO_CONFIG_INVALID`) and incompatible with `--url` (`LOUSHO_CONFIG_CONFLICTING_OPTIONS`); under `CI`, cassette mode defaults to `auto`. `--judge` flips the include globs to `*.judge.eval.*` and sets `LOUSHO_ALLOW_LLM_JUDGE=1`; `--url <base> [--token]` reroutes cases at a deployed agent (`src/evals/remoteTarget.ts`, token defaults to `LOUSHO_EVAL_TOKEN`, never printed); `--config` substitutes the user's vitest config and turns globs into vitest filters.
- **`doctor`** (`doctor.ts` + `doctorCore.ts` + `doctorChecks.ts` + `doctorSpec.ts`): `buildEnvironment()` injects the real `DoctorEnvironment` (process.versions, env, `createRequire`-based package resolution — `resolveVersion` walks up to the manifest *named* the package because exports maps can land on a nested package.json, `fetch`, `commandExists` scanning `PATH`/`PATHEXT`, a 2 s `dockerode` ping). `runDoctor()` is pure over that: Node `engines` (`versionRange.satisfiesRange`), required peers (`ai`, `zod`), optional provider/feature peers paired to the installed `ai` major (`installedAiMajor`, `providerPeers`, `FEATURE_PEERS`), provider env vars (reports set/not-set — never values), the default `createAgent()` provider via `modelFromEnv`, Ollama reachability when relevant (2 s `/api/tags` probe), Docker when the spec uses a sandboxed tool, and spec checks (`inspectSpec`: provider type known, tools resolve, sandbox flags feed `SpecNeeds`, MCP servers, policy). `--json` renders machine-readable; `renderReport` colors on TTY unless `NO_COLOR`; exit 1 if any check fails.
- **`mcp`** (`mcp.ts`): `loadSpec` → `specToAgent` → `serveMcp` on stdio (default, stdout is protocol-only — even the "serving on" line goes to stderr) or `--http --port 3920`.
- **`add`** (`add.ts` + `registry.ts` + `addCheck.ts` + `addWrite.ts` + `addReceipt.ts`): registry install — index/item loading, manifest print, code-vs-manifest check, safe writes, receipt. See [registry and kits](/ship/registry-kits).
- **`init`** (`init.ts` + `init/`): the scaffolder — options, prompts, scaffold and templates live in the `init/` subdirectory. See [create-lousho-agent](/ship/create-lousho-agent).
- **`studio`** (`studio.ts`): `resolveAgentForgeDir` locates `apps/agent-forge` (repo root or installed package root), then `startStudio` auto-detects prod (prebuilt `dist-server` — what published installs run, one process serving API + static UI) vs dev (`tsx` server + Vite HMR, monorepo only); `--prod`/`--dev` force, and combining them is a `usageError`. Child processes deliberately, never imported — Agent Forge is a separate workspace package.
- **`traces`** (`traces.ts`): reads only the `fileTraceExporter()` output dir (`.lousho/traces` by default) via `findTraces`/`listTraces`/`readTrace` — `lousho traces` lists runs newest-first, `lousho traces <id|prefix>` prints one as a span tree (`--content` includes payloads, `--json` for machine output). Imports `src/traces/` only, never the run loop.

## Design decisions

- **Lazy `require()` per command** keeps `lousho` startup cheap; each `dist/cli/*.js` is a self-contained bundled entry, so no command pays for another's imports.
- **Exit codes, not `process.exit()`** — `run*` functions resolve with the code and `bin` assigns `process.exitCode`, which is why every command's tests can call it in-process (`EvalDeps`, `AddIo`, `InitEnvironment`, `ChatIo` are injection seams).
- **One parser, one error style** — every flag mistake is `LOUSHO_CONFIG_INVALID` with the usage as the hint. `init` is the deliberate exception (`InitUsageError`, plain message) because it predates the shared parser and its prompts make usage-hints noise.
- **vitest is the user's dependency** — `eval` never bundles a runner; it resolves vitest from the project so the eval files compile against the same toolchain as the project's tests.
- **Localhost by default** — `dev`, `mcp --http`, and the generated server all bind `127.0.0.1` unless a host is explicitly given.
- **Help is a parse result, not a side effect** — every `parse*Args` returns `help: true` and its `run*` prints `USAGE` and exits 0, so `-h` never triggers the rest of validation (an unknown flag *alongside* `-h` still errors, which strict `parseArgs` gives for free).
- **Commands own their USAGE string** — the canonical usage line lives next to each command's `CommandSpec` (and again in `bin/lousho.js`'s `USAGE` for the summary), so flag docs and parse errors can't drift apart.
- **Doc comments name their tickets** — every command module header carries its LOU-* references (LOU-H6 dev, LOU-D8 eval, LOU-I1 build, LOU-D50 add, LOU-Z6 acp, LOU-D3 init); grep a ticket id to find the spec that motivated the code. `src/cli/__fixtures__/` holds the spec/agent-dir/module/eval trees the command tests run against.

## Example

`lousho build ./agent --target=docker` flows end to end:

1. `bin/lousho.js` → `COMMANDS.get('build')` → lazy `require('../dist/cli/build.js')` → `runBuild(rest)`.
2. `parseBuildArgs` — positional `./agent` becomes `agent`; `--target=docker` binds via `=`.
3. `getAdapter('docker')` — `DockerAdapter` (registered by `registerBuiltInAdapters()` at module load, alongside the `stub` test adapter).
4. `driveAdapter` → `DockerAdapter.scaffold(agentDir, '.lousho/build/docker')` → `DockerAdapter.build(outDir)` → `describe()` printed on stdout: `docker build -t lousho-agent . && docker run -p 3000:3000 lousho-agent`. Exit 0; any thrown error prints `Error: <message>` on stderr and exits 1.

The same skeleton — `parse*Args` → `run*` → exit code — is the shape of every command above; learn one and you've learned the CLI.
