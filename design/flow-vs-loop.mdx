## The decision

The SDK keeps **two** ways to sequence model work. The agent loop (`AgentExecutor`) asks the model what to do next on every turn — open-ended, bounded by `maxSteps`, budgets, permissions and approvals. `FlowExecutor` (`src/flows/FlowExecutor.ts`) executes a fixed graph of `sequence` / `parallel` / `oneOf` / `forEach` / `llmCall` / `toolCall` / `setVariable` / `evaluator` / `return` / `end` / `throw` nodes — the *harness* decides the order, and the model only fills `llmCall` nodes. When the pipeline is known in advance, deterministic orchestration wins: the model cannot skip the verify phase, reorder the spec→plan→implement ladder, or forget the merge step after a parallel fan-out (`examples/phase-pipeline`, `examples/waves`).

## Alternatives rejected

- **Prompting the loop into compliance.** "Always verify after editing" in a system prompt is a suggestion the model follows most of the time; a flow's `oneOf` chain makes the retry ladder structural. Phase/wave patterns need *guaranteed* ordering — that is the whole reason flows exist.
- **Loops inside the executor.** `LoopNode` (`type: 'loop'`, `maxIterations`, `condition`, `loopFlow`) is an **editor-side shape only** (`EditorShapeStep` in `src/types/flow.ts`): it has no entry in `FlowExecutor`'s handler map, so a `loop` reaching `dispatchNode` throws `LOUSHO_FLOW_INVALID`. The runtime shapes (`RuntimeStep`) are a smaller, total set; repetition at run time goes through `forEach` over known items, and anything genuinely open-ended belongs to the agent loop. *(Inference: keeping unbounded "run until condition" graphs out of the executor keeps every flow run finite except through `forEach` item counts and the `maxDepth` guard — default 100 — while visual editors keep the richer node set.)*
- **`return` as control flow.** A `return`/`end` node just resolves its `value` — it does **not** early-exit a `sequence` (`executeSequence` runs every step and yields the last result). Early exit is expressed with `oneOf` branch selection, which is why routing flows put `return` nodes *inside* options. This matches the node-as-value-producer model: every node evaluates to something; `oneOf` is the only brancher.
- **`eval`/`new Function` for conditions.** Flow definitions can come from untrusted editors and registries, so `oneOf` conditions and `evaluator` expressions run through `evaluateSafeExpression` (`src/flows/safeExpression.ts`) — a hand-written recursive-descent evaluator that never compiles host code, rejects `constructor`/`__proto__`/globals/assignment, and allow-lists only `includes`/`startsWith`/`endsWith`. Crucially, `{{name}}` placeholders are *bound as values*, never pasted into expression text — a variable containing `x' === 'x' || 'a` is data, not an injection.

## Where it shows up

- `src/flows/FlowExecutor.ts` — the static, instance-free executor: per-type handler map, `step-start`/`step-complete`/`step-error` events, OTel `flow.node`/`chat`/`execute_tool` spans, sandbox routing via `executeToolWithSandboxGuard`.
- `src/flows/safeExpression.ts` — the expression grammar (`docs/flows.md#flow-expressions`).
- `src/types/flow.ts` — the deliberate split: `EditorShapeStep` (what editors produce: `step`, `loop`, `condition`, `bestOfAll`, `uiComponent`, `tool`, …) vs `RuntimeStep` (what the executor runs).
- `src/flows/FlowBuilder.ts`, `validators.ts` — metadata builder plus validation; `isCreateAgentResult` rejects a live agent as `context.agent` (LOU-R14) — a flow's steps run under a plain `AgentConfig` (`{ name, prompt?, settings }`), because a `createAgent()` agent runs *itself*.

Two interpolation regimes, deliberately different: prompts and tool arguments use flat `{{var}}` text substitution (regex `\{\{(\w+)\}\}`, `toString()`, missing → `''`; `interpolate`/`resolveValue`/`$var` references) — dumb and predictable, because the output is model input. Branch conditions use the safe-expression grammar, because they decide control flow.

## Trade-offs accepted

- **Flows lose the loop's guardrails.** A `toolCall` node goes through the sandbox guard but *not* the approval gate, hooks, permission modes, or checkpointing — no pause-for-human, no resume, no `needsApproval`. Durable or gated work must call the executor/agent loop, not a flow.
- Two syntaxes to learn (`{{var}}` in prompts vs expression grammar in conditions), and the flat interpolation can't reach nested paths (`{{user.name}}` doesn't match `\w+` — use `setVariable`/`evaluator` or `$` references).
- Editor/executor duality: a node type that exists in `EditorShapeStep` but not `RuntimeStep` fails at run time, not at build time — the editor must lower it.
- The executor predates the store/session machinery; bridging them is examples-level work today (`phase-pipeline` orchestrates agents *around* flows).

## Example

```ts
// a routing decision the model can't skip or reorder
const steps: EditorStep = {
  type: 'sequence',
  steps: [
    { type: 'llmCall', prompt: 'Classify: {{message}}', outputVariable: 'category' },
    {
      type: 'oneOf',
      options: [
        { condition: "'{{category}}' === 'billing'", step: billingFlow },
        { condition: 'confidence >= 0.7', step: autoReply },   // bound as a value
        { step: humanReview },                                // no condition = default
      ],
    },
  ],
};
```
