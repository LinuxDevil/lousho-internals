---
title: "ACP (Agent Client Protocol)"
description: "How serveAcp bridges JSON-RPC-over-stdio (Zed and other editors) to SDK sessions: event→session/update mapping, permission requests, questions and sign-ins."
---

`serveAcp()` (`src/acp/serveAcp.ts`) serves an agent over the [Agent Client Protocol](https://agentclientprotocol.com) v1: JSON-RPC 2.0, one JSON message per line. It is transport-independent — it reads lines from `options.input` and hands outgoing lines to `options.write`; `lousho acp` (`src/cli/acp.ts`) wires those to stdin/stdout and forces `console.*` to stderr (`withConsoleOnStderr`), because stdout must carry nothing but protocol frames.

## Entry points

| Symbol | File | Role |
| --- | --- | --- |
| `serveAcp(agent, { input, write, store? })` | `src/acp/serveAcp.ts` | The protocol loop; runs until `input` ends, then aborts in-flight prompts and settles. |
| `runAcp`, `parseAcpArgs` | `src/cli/acp.ts` | The CLI: `lousho acp <spec.yaml\|spec.json\|agent-dir\|agent.ts> [--model provider/model]`; loads the target like `lousho chat`. |

## How it works

The server keeps `sessions: Map<acpSessionId, { sdk: AgentSession, abort?, question? }>` and `waiting: Map<requestId, resolve>` for agent→client requests.

| ACP message | Handling |
| --- | --- |
| `initialize` | `{ protocolVersion: 1, agentCapabilities: { loadSession: false, promptCapabilities: text-only }, authMethods: [] }`. |
| `session/new` | One ACP session = one SDK session (`agent.session({ id: 'acp-<newId>' })`), so prompts share history. `cwd`/`mcpServers` are ignored — the agent's own config owns both. |
| `session/prompt` | `promptText` joins `text` blocks and `resource_link` blocks (as Markdown links); anything else is dropped, and an all-empty prompt is `-32602`. Runs `turn()`; resolves `{ stopReason }`. |
| `session/cancel` (notification) | Aborts the session's `AbortController`; the in-flight prompt resolves `cancelled`. |
| → `session/update` | The run's `AgentEvent`s, mapped by the `UPDATES` table. |
| → `session/request_permission` | A tool approval, as an agent→client request with `allow`/`reject_once` options. |

`UPDATES` is the whole bridge in one table: `text.delta` → `agent_message_chunk`, `reasoning.delta` → `agent_thought_chunk`, `tool.start` → `tool_call` (`status: in_progress`, `rawInput: args`), `tool.resume`/`tool.done`/`tool.error` → `tool_call_update` (`in_progress`/`completed`/`failed`, result as `content` + `rawOutput`). Sub-agent events produce no update — they stay inside their parent's tool call, matching the SSE/UI convention.

The pause loop in `turn()` handles the three approval kinds:

- **tool approval** → `permit()` sends `session/request_permission`; the decision runs via `agent.approvals.streamResolve()` and its events stream back through the same `relay`. After a cancel, the decision runs under the aborted signal so the approval still settles.
- **`kind: 'question'`** → `ask()` emits the question (with numbered options) as an `agent_message_chunk`, ends the turn with `stop` and remembers the `approvalId`; the *next* `session/prompt` is routed to `approvals.streamAnswer` instead of `session.stream`.
- **`kind: 'sign-in'`** → `signIn()` shows the link, then loops `permit()` ("I've signed in") → `streamResolve(approved: true)` → `awaitSignInGate`: approving before the callback lands returns `pending` and the client is asked again; reject resolves `approved: false` and relays the cancellation.

Errors: a JSON parse failure is `-32700`; an unknown method `-32601`; a handler failure becomes `-32603` whose `data.code` is extracted from the `LOUSHO_*` marker in the message (`toRpcError`). `stopReason` maps via `STOP_REASONS` (`max-steps`→`max_turn_requests`, `budget-exceeded`/`length`→`max_tokens`, `guardrail`/`content_filter`→`refusal`, `aborted`→`cancelled`, else `end_turn`); a run ending in `error` throws `LOUSHO_AGENT_EXECUTION_FAILED` as an RPC error.

## Design decisions

- **ndjson, no LSP-style framing.** ACP is one JSON object per line; `serveAcp` takes `AsyncIterable<string>` precisely so tests feed arrays and the CLI feeds `readline` — the protocol never sees a socket.
- **One ACP session = one SDK session.** History, pending turns and (with `store`) durability come free from `AgentSession`; `loadSession: false` because the SDK's resume model doesn't map onto ACP's.
- **Approvals are agent→client requests, not updates.** `request()`/`waiting` implement ACP's reverse-direction RPC: the agent sends `session/request_permission` with an id and parks until the client's response (or an abort, which fabricates `outcome: cancelled`). This is why an editor's native approve/deny UI works unchanged.
- **A question is a turn boundary, not a pause inside one.** ACP has no "answer" primitive; ending the turn and routing the next prompt to `streamAnswer` fits the editor's mental model (the question is just agent output; the reply is just user input).
- **Sign-in re-asks rather than blocking.** The editor is the browser's neighbour: the link is shown, "allow" means "I've signed in", and `awaitSignInGate` detects the not-yet-signed-in `SignInPendingError` so the prompt loops until the callback lands or the user cancels.
- **`store` defaults to the agent's own.** Pass an explicit `AgentStore` when ACP transcripts should live somewhere other than the agent's default (e.g. a throwaway memory store).

## Example

```bash
# Serve an agent directory to Zed:
lousho acp ./my-agent --model openai/gpt-4o
```

```json
// Zed settings.json
{ "agent_servers": { "My agent": { "type": "custom", "command": "npx", "args": ["lousho", "acp", "/path/to/my-agent"] } } }
```

```ts
// Embedded (tests, other transports):
import { serveAcp } from '@lousho/build-ai-agent';

const out: string[] = [];
await serveAcp(agent, {
  input: (async function* () { yield* ['{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}']; })(),
  write: (line) => out.push(line),
});
```
