## What this is

The workspace tools are the SDK's built-in file-and-shell toolkit: `read_file`, `write_file`, `edit_file`, `list_dir`, `glob`, `grep`, and `shell`. They give a coding agent filesystem and shell access without ever touching `node:fs` or `node:child_process` themselves — every call goes through two small interfaces, `FsProvider` and `ShellProvider`, so the same tools run against a real directory, an in-memory tree for tests, or a remote sandbox (LOU-X6). Think of the tools as a universal remote and the provider as whichever device is plugged in.

## The mental model

```mermaid
flowchart LR
    A["fs + shell tools"] --> B["Lexical path check"]
    B --> C["realpath check"]
    C --> D["FsProvider / ShellProvider"]
    D --> E["Disk, memory, or sandbox"]
    F["Checkpoints"] -.-> A
```

Five nouns to hold onto:

- **Provider interfaces** — `FsProvider`/`ShellProvider`, the only things the tools call.
- **Two confinement layers** — a lexical check on the path text, then a `realpath` check on what it resolves to.
- **Command policy** — `allow`/`deny` patterns on shell commands, checked before any approval prompt.
- **Checkpoints** — before-the-write file backups that make `rewind` possible.
- **Keyed queue** — per-path serialization so two writes never interleave.

## How it works

1. **Tools wrap providers.** `createFsTools(fs, options)` (`src/tools/workspace/fsTools.ts`) builds six `defineTool()` wrappers over an `FsProvider`; `createShellTool(shell, options)` (`shellTool.ts`) builds one `shell` tool over a `ShellProvider`. Every path argument is a workspace-relative `/`-separated string — the model never sees a host path. Provider rejections are caught and turned into `WorkspaceError`s that reach the model as ordinary tool errors, never exceptions that end a run.
2. **Layer one checks the path text.** `normalizeWorkspacePath()` (`paths.ts`) does lexical normalization shared by every provider: rejects NUL bytes, absolute and UNC paths, drive letters, and any `..` climbing above the root; treats backslashes as separators so `a\..\..\b` can't sneak a `..` through; on `win32` additionally rejects `:` (drive letters, alternate data streams), reserved device names (`CON`, `NUL`, `COM1`…), and segments made only of dots and spaces (Windows silently strips them — `'.. '` opens `'..'`).
3. **Layer two checks what the path resolves to.** `NodeWorkspace.resolve()` adds `realpath` on the deepest existing ancestor, so a symlink inside the root pointing outside is rejected — including for files that don't exist yet — and a *dangling* symlink in the path is refused outright (following it on write could create a file outside the root). `rm` uses `followFinalLink: false` so it deletes a link, never its target.
4. **The provider does the work.** `NodeWorkspace` is a real directory plus `child_process`; `MemoryWorkspace` is the test double; `SandboxShell` runs `sh -c "<command>"` through a `SandboxAdapter` — e.g. `SubprocessSandbox` (`src/security/sandbox.ts`) runs each command in a fresh, network-less container that sees only the bind-mounted `cwd`. `NodeWorkspace`'s own shell is explicitly **not** a sandbox: a command can do anything the OS user can.
5. **Checkpoints capture before the write.** Pass `new WorkspaceCheckpoints(fs)` as `createFsTools(fs, { checkpoints })` (N7). `track(ctx, path, write)` captures the file's content and mode *before* the write, runs the write, then records a `WorkspaceFileBackup`. `rewind(toTurn)` restores every file changed in that turn or later.
6. **A keyed queue serializes writes.** `KeyedQueue` (`keyedQueue.ts` — an 18-line promise chain where each key's tail is the previous task's promise) runs async work one-at-a-time per key: `track()` uses it so two writes to the same path never interleave capture/write/record, and the file store uses it per session file.

## Under the hood

- **The fs tools stay small and model-ergonomic.** `read_file` returns numbered lines (`   12\tcode`) with `offset`/`limit` paging, refuses files over 10 MB, and detects binary (`\0`); `edit_file` does exact-match replacement requiring uniqueness unless `replace_all`, with a CRLF hint on miss; `list_dir` sorts and suffixes directories with `/`; `glob`/`grep` prefer `FsProvider.glob` when a backend offers it, else `walkFiles()` does a BFS that never follows symlinks, skips `['.git', 'node_modules']` by default, and stops at `maxFilesScanned` (20k). All outputs are capped (`maxReadLines` 2000, `maxOutputChars` 50k, `maxResults` 200) with explicit truncation markers so the model knows to narrow. `readOnly: true` emits only `read_file`/`list_dir`/`glob`/`grep`.
- **Annotations drive modes.** Read tools carry `annotations: { readOnlyHint: true, destructiveHint: false }` ([plan mode](/core/permission-modes) lets them through); `write_file`/`edit_file` carry `editsFiles: true` (acceptEdits mode).
- **The shell tool is safe by default:** `needsApproval` defaults to `true`. `allow`/`deny` `CommandPattern`s are checked *before* approval is ever asked — a denied command is a tool error, not a prompt. String patterns match exactly or as a prefix followed by whitespace, and a command matched only by string patterns may not contain shell operators (`; & | \` $( < >`, newline), so `git status; rm -rf ~` never passes as `git status`. Deny strings are tested against every `;`/`&`/`|`-separated part. The doc comment is blunt: a deny list is a convenience, not a security boundary.
- **Process execution** (`nodeProcess.ts`) spawns via the workspace shell (`/bin/sh` or `%ComSpec%`), collects stdout/stderr keeping head + tail up to `maxOutputBytes` (1 MB), and kills the whole process tree on timeout or abort — `taskkill /T /F` on Windows, `process.kill(-pid)` on the detached process group elsewhere. Environment is minimal by default (`commandEnv` in `src/security/commandEnv.ts`: `PATH`, `HOME`, `USERPROFILE`, `TMP/TEMP/TMPDIR`, `LANG`, `TERM`, `LC_*`, plus `SystemRoot`/`ComSpec`/`PATHEXT`/`WINDIR` on Windows); `inheritEnv` adds named variables, `true` passes everything including API keys — flagged in docs as only for trusted commands.
- **Sandbox abort is a race.** `SandboxShell` races a promise against the adapter call so even an adapter that ignores the signal stops being awaited at once.
- **Checkpoint records** carry `sessionId` (`ctx.sessionId` minus a `.turn-<n>` suffix), `turn` (the 0-based index of the user message being answered), and `afterHash` (sha256 of what was written). Files over `maxFileBytes` (1 MB) record `omitted: 'too-large'`; a second write to a path already backed up in the same turn records `omitted: 'same-turn'` — only the first backup is needed to rewind. Rewind deletes agent-created files, restores content + mode on overwritten ones, and skips a file whose current content no longer matches the last `afterHash` as `'changed-since'` unless `force`. `dryRun` returns the same `RewindResult` without writing; a real rewind plans every path (reads only) before anything is written. `maxTurns` (20) prunes old turns via `removeBeforeTurn`.
- **The file store persists rewind across restarts.** `FileWorkspaceCheckpointStore` writes one JSON file per session — rename-with-retry for Windows' EPERM/EBUSY locks; non-name-safe session ids are hashed.

## Example

```ts
import { NodeWorkspace, SandboxShell, SubprocessSandbox, WorkspaceCheckpoints,
         createFsTools, createShellTool } from '@lousho/build-ai-agent';

const workspace = new NodeWorkspace({ root: './project' });
const checkpoints = new WorkspaceCheckpoints(workspace);

const tools = [
  ...createFsTools(workspace, { checkpoints, needsApproval: { write_file: true } }),
  createShellTool(new SandboxShell(new SubprocessSandbox({ image: 'node:20-alpine' }),
                                  { cwd: '/abs/path/to/project' }),
                  { deny: [/\bsudo\b/], needsApproval: (cmd) => !/^git (status|diff|log)\b/.test(cmd) }),
];
```

`NodeWorkspace` gives the fs tools a real `./project` directory with both confinement layers. `WorkspaceCheckpoints` wraps that same provider so every write is backed up first. `createFsTools` emits the six fs tools, with `write_file` gated on human approval. `createShellTool` runs commands inside a fresh `node:20-alpine` container via `SandboxShell`; its policy denies anything matching `sudo` outright, auto-approves read-only `git status/diff/log`, and asks for everything else.

## Design decisions

- **Interfaces, not `fs`.** Tools depend on `FsProvider`/`ShellProvider` so E2B/Daytona/Cloudflare backends drop in; a provider exposed to a model must still confine paths itself (`NodeWorkspace` is the reference).
- **Two-layer confinement.** Lexical checks are cheap and shared; `realpath` catches what lexical analysis can't (symlinks). Neither alone is sufficient.
- **Policy before approval.** `allow`/`deny` are evaluated in `needsApproval` *and* re-checked in `execute` — a refused command never becomes a human prompt, and approval can't whitelist past it.
- **Checkpoints are a separate object.** `WorkspaceCheckpoints` wraps any `FsProvider`, works with user-written providers, and restores through the provider's own confinement.
- **Errors are model-readable.** `WorkspaceError` messages name the workspace path (never host paths) and suggest the fix (`"Use a path relative to the workspace root"`).
